# Survival and time-to-event figures

Use when the question concerns time until an event, not merely a response measured repeatedly over time. The design case is [Nature Fig. 3 in the survival/benchmark review](journal-learning-2026-10-25-survival-benchmark.md). These are analysis and drawing instructions, not a bundled, tested survival implementation.

## Define the estimand before selecting a curve

- Establish subject ID, eligibility, time origin, time unit, entry time if delayed, event definition, event code, competing events, follow-up end and censoring rule. Check event counts separately from subject counts; cells or repeated records do not increase independent patient n. Confirm that exposure/group membership is defined at the stated analysis origin; post-baseline grouping needs an appropriate analysis rather than retrospectively labelling baseline curves.
- Distinguish survival probability, event cumulative incidence and hazard. For an ordinary single-event survival question, Kaplan–Meier is a step estimate. For absolute probability of a specified event with competing events, use a suitable cumulative-incidence estimator, such as the relevant Aalen–Johansen state probability; do not label one minus a Kaplan–Meier curve that censors competing events as that absolute probability. Cause-specific hazard modelling answers a different question and can legitimately handle competing events differently.
- Save the group definition, cutoff, scale/normalization and justification. A displayed high/low split is an analytical choice, not an aesthetic default. Do not optimize a cutoff using the outcomes and present the selected comparison as prespecified. Consider a continuous analysis when appropriate; do not invent a model or hazard ratio just to accompany a curve.

## Draw estimates, censoring and support together

- Use the fitted object's step geometry. Do not spline/LOESS-smooth an empirical survival curve. Explain censor symbols and locate them at the appropriate fitted curve height; they are not outcome events. Distinguish an observed last event from the last follow-up time.
- State whether intervals are shown, their confidence level and construction. Pointwise confidence intervals are not simultaneous bands. Missing intervals in a reference figure are not a reason to omit uncertainty from a new figure where it matters.
- Give probability axes explicit units (0–1 or %), time units and the endpoint. Default to the complete probability range; any focused range must be prominent and must not conceal clinically/scientifically relevant context. Align comparable curves on the same time/probability scales.
- Add a number-at-risk table when it is needed to judge follow-up support, especially for group comparisons with long or sparse tails. Use the same group order, time ticks, x mapping and colours/line types as the curves. Initial group n is not a replacement for changing risk counts. Label `at risk`, `events` and `censored` separately; state whether event/censor counts are cumulative or since the previous displayed time.
- Declare any display horizon or sparse-tail rule and retain the full analysis record. Do not extend a flat curve past supported follow-up or remove an inconvenient late crossing. Inspect confidence intervals and risk counts together before interpreting tail separation.
- Place each comparison's endpoint and group/cell-neighbourhood label locally. Readers should not have to infer which of several adjacent curves is which from left/right wording deep in a caption. Keep heatmap enrichment, marker magnitude and survival group identity in separate colour mappings.

## Statistics and prose

Report the actual test/model, sidedness where relevant, adjustment, independent n, event count and missing-data population. A log-rank P value is not an effect size or an adjusted causal comparison. If reporting an HR, time-specific survival difference or restricted mean survival contrast, obtain it from an appropriate analysis with its uncertainty and assumptions; do not estimate it from a screenshot. Check proportional-hazards assumptions when that model underlies the claim. State observational and confounding limits without converting association into treatment benefit. Do not infer that a study omitted a method merely because it is absent from one caption.

## RStudio implementation contract and checks

1. Reuse the project's R environment; inspect the installed `survival` package before adding anything. Encode events explicitly, for example as a verified logical condition, instead of relying on automatic 0/1 versus 1/2 interpretation. Construct the appropriate `survival::Surv()` object, including entry/exit intervals when required, then fit the estimand with an appropriate method.
2. Derive curve coordinates, intervals, censor marks and risk-table values from the same fit and analysis population. `summary.survfit()` documents survival at time t+0 and `n.risk` at t−0. Requested-time event/censor counts may aggregate over the preceding displayed interval: check the arguments and label the actual convention. For delayed entry/counting-process data, verify requested-time risk counts against entry/exit records and subject IDs; the documentation warns that arbitrary requested times can otherwise produce misleading counts. Do not use `extend=TRUE` just to fill a table past follow-up.
3. Reuse `group_levels`, `group_colors`, `group_linetypes`, `data_line_mm`, font and dimension fields from `figure_config.R`. Add and wire project-specific fields for endpoint/time origin, event codes, group cutoff, time breaks/horizon, interval method/level, censor symbol and risk-table height. These fields are **not already implemented** in the bundled template. Align the curve and risk subpanel using the existing layout tools; inspect alignment after legends and axis titles are added.
4. Run saved R code in RStudio and inspect steps, censor marks, risk counts, crossings, tails, final-size text and exported files. Independently check selected risk-table cells against the analysis records. Apply colour-vision and grayscale checks to overlapping lines and symbols, not just swatches. Store analysis provenance, cutoff choices, package versions and the export QA result.
