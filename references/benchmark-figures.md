# Multi-metric benchmark and ranking figures

Use for model/method comparisons with several metrics, preprocessing variants or datasets. Design evidence: [Luecken et al. Fig. 2 review](journal-learning-2026-10-25-survival-benchmark.md). A ranked matrix communicates a specified evaluation; it is not a universal leaderboard or a substitute for matched-data validation.

## Keep scores, ranks and preferences distinct

- Key each result by method, configuration, task, split/seed, metric and output type. Record raw score, unit, direction, transformation, normalization basis and eligibility. Different preprocessing/output variants are different runs; do not collapse them under one method label without a declared selection rule.
- Before aggregation, define which metrics belong to each category, their direction, within-category weights and between-category weights. Average scores and then rank only if that is the chosen method; averaging ranks is a different operation. Display category scores beside the overall score when the trade-off matters. Do not copy the source paper's 40/60 weights into unrelated research.
- For min–max normalization, save the reference candidate/task set and the actual bounds. New candidates or extremes can change normalized scores and weighted order. Handle constant metrics explicitly when max = min. A normalized 100% is not necessarily perfect scientific performance or absolute accuracy. Keep raw values available.
- Differentiate missing, not applicable, failed, timed out and true zero. Explain eligibility and aggregation denominators. Do not make an unavailable metric a tiny zero-size dot or quietly average a different metric set per method. If available-case aggregation is justified, report metric coverage and sensitivity to a common metric set. Identify failure rules separately from score values.
- Predeclare tie handling, rounding and variant selection. Keep full-precision scores for ordering, and show uncertainty or task/seed variation when available. If a ranking drives a conclusion, examine plausible weights, normalization choices and tasks rather than declaring a winner from one visually convenient weighting. Report an inconclusive or preference-dependent order when warranted.

## Make the matrix readable

- Use aligned rows for variants and grouped metric headers for related questions. Preserve stable row IDs across views. A method's category colour and a metric's performance scale are different semantics; label them separately.
- If colour shows rank and size/length shows score, give separate legends and directional labels, including whether rank 1 is best. Use area-proportional circles for quantitative score magnitude; do not accidentally make radius proportional. Quantitative bars start from a defined zero. When exact comparisons matter, a dot plot on a common numeric axis or a numeric table may be clearer than redundant colour/size encoding.
- Explicitly label any omitted middle rows and provide the complete comparison table or supplemental plot. A top/bottom excerpt must not imply that adjacent displayed rows are adjacent ranks. Distinguish an unintegrated/control baseline, a method variant and a failed run.
- Long metric names need enough width, abbreviations defined nearby or a transposed/separate table; rotated labels are a choice to test at print size. Do not shrink an oversized matrix until its legend is unreadable. Use restrained row guides and separate missing-state symbols.
- Pair an overview with diagnostic views only when they answer a different question. For UMAP/t-SNE, follow [embedding rules](embedding-atlas-figures.md): reuse ID-keyed coordinates while recolouring within each method, give cell identity and batch separate legends, and do not infer superiority from island shape. An attractive embedding does not validate a weighted score.

## RStudio implementation and delivery

Keep metric transformations, aggregation, tie handling and variant selection in a separate R analysis script. Supply a long results table with availability/status fields plus an exported table of raw, normalized, category and overall scores. Recompute selected displayed rows from this table before drawing. Define task/configuration factor levels and annotation mappings explicitly; use ggplot2 geometry and the existing assembly tools.

Reuse the central font, dimensions, spacing and export settings. Add and wire project-specific `metric_direction`, `metric_groups`, `normalization_bounds`, `metric_weights`, `category_weights`, `missing_policy`, `tie_rule` and `shown_rows`; these are proposed project fields, **not existing scaffold features**. For size encoding, select a scale with the intended area semantics and verify the legend against known values. Keep rank scales independent of raw-score scales. Execute the saved R code in RStudio and verify final-size labels, colour/gray accessibility, omitted-row notices, baseline labels and the exported score table.

The caption should identify task/test population, metrics and direction, aggregation and normalization, weights, missing/failure policy, shown subset, repeated runs/uncertainty and where complete results are available. State the ranking's scope in Results. Exact source method details and limits are in the linked review; no benchmark was rerun as part of that reference analysis.

## Weight-simplex winners and rank uncertainty

Use for a fixed option set with criteria, declared scoring/normalization and three nonnegative weights closing to one. A ternary winner map answers which option is first at each evaluated weight; a rank-probability matrix answers how order varies under a specified perturbation experiment. They are not interchangeable with a ternary continuous mixture-response surface. Require the scoring method and perturbation design before claiming either. See [the ranking reference review](reference-observations-2026-11-12-robustness-sensitivity-ranking.md).

- Encode winner identity with stable category colours and direct option labels; do not interpolate IDs or blur boundaries into a continuous gradient. Preserve corner order, equal aspect, baseline weights, grid resolution and tie status. Describe cell-centroid or other assignment explicitly. More than three free weights need a defined slice/aggregation or a different view, not a forced triangle.
- A winner region's geometric area is not its first-place probability unless the declared weight distribution and integration support that equivalence. Recompute scores under each draw using the documented normalization/reference-set policy. Joint indicator error, benefit/cost directions, clipping and dependent perturbations all affect the experiment; do not adopt a reference image's distribution as a default.
- Build the complete option-by-rank table before drawing area-proportional bubbles (`scale_size_area`) with a quantitative size key. State whether ties are broken or fractionally allocated and how invalid draws affect denominators. For full rankings with consistent tie allocation, each option's rank probabilities sum to one before rounding; resolve exceptions explicitly. Text-label cutoffs may reduce crowding but must not remove low-probability marks or turn a missing value into zero; provide the full numeric table when precision matters.
- Compare weight-only, indicator-only and joint perturbations with the same underlying paired draws and categorical offsets/shape redundancy. These contrasts are experiment-conditional probabilities, not real-world preference frequencies or an additive variance decomposition. Report Monte Carlo resolution/uncertainty only when computed with the relevant draw design.
- Keep a common 0–1 probability axis for the overview. For near-zero overlaps, use a labelled inset showing all options in a predeclared range, or provide exact values; preserve the overview and link the inset's IDs. Do not selectively enlarge only a favoured option or fill empty space without an evidential purpose.
- Store proposed `criterion_direction`, `weight_grid`, `weight_draw_id`, `indicator_draw_id`, `normalization_policy`, `tie_rule` and `label_cutoff` in project analysis/configuration and bind them to polygons, point sizes and comparison marks. Recheck a vertex, baseline and boundary cells, probability totals and paired draws before export. These are workflow instructions, not a bundled TOPSIS engine or automatic statistical validity guarantee.
